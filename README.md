# Ledgerline

A simulated payments backend. It moves money between accounts and guarantees that money is never
created, lost or duplicated — even when requests arrive concurrently, a client retries, or the
server crashes halfway through.

Accounts are customers, merchants, and one system **funding** account that stands in for the outside
world. Money movement is written as balanced ledger entries that always sum to zero.

- **Stack:** Java 21, Spring Boot 3.5, PostgreSQL 16, Flyway, JPA/Hibernate, JUnit 5 + Testcontainers
- **Status:** Sprint 0 complete (accounts slice). Money movement lands in Sprints 1–4.

---

## Running it

Requirements: JDK 21, Docker (for PostgreSQL and for the integration tests).

```bash
# 1. start PostgreSQL (Flyway applies the migrations on first boot)
docker compose up -d

# 2. run the app
./mvnw spring-boot:run          # http://localhost:8080

# 3. run the tests (they start their own throwaway PostgreSQL via Testcontainers)
./mvnw test
```

The app connects to `localhost:5432/lp_db` as `lp_user` / `lp_password`. Override with the
`POSTGRES_URL`, `POSTGRES_USER` and `POSTGRES_PASSWORD` environment variables.

## The API

All endpoints live under `/api/v1`.

| Method and path | Purpose | Success |
| --- | --- | --- |
| `POST /api/v1/accounts` | Create an account (`ownerName`, `type`) | 201 + `Location` |
| `GET /api/v1/accounts/{publicId}` | Account and current balance | 200 |

```bash
# create
curl -X POST localhost:8080/api/v1/accounts \
  -H 'Content-Type: application/json' \
  -d '{"ownerName":"Ravi Kumar","type":"CUSTOMER"}'

# {"publicId":"0b72e5bf-...","ownerName":"Ravi Kumar","type":"CUSTOMER",
#  "currency":"INR","balancePaise":0,"status":"ACTIVE","createdAt":"..."}

# read back
curl localhost:8080/api/v1/accounts/0b72e5bf-3d9a-4bce-ae5f-1a71ef678b56
```

`public_id` is a UUID generated by the server. Clients never choose it; they receive it in the
`201` response and use it from then on.

### Errors

Every error returns the same shape — a stable machine-readable code plus a human message:

```json
{"code":"ACCOUNT_NOT_FOUND","message":"Account with publicId ... not found","timestamp":"..."}
```

| HTTP | Code | When |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | Validation failed, malformed body, unparseable id |
| 404 | `ACCOUNT_NOT_FOUND` | Account does not exist |
| 409 | `REQUEST_IN_PROGRESS` | Same idempotency key is still being processed |
| 422 | `INSUFFICIENT_FUNDS` | Source balance is below the amount |
| 422 | `ACCOUNT_FROZEN` | An account in the request is frozen |
| 422 | `IDEMPOTENCY_KEY_REUSED` | Same key, different request body |
| 503 | `RETRYABLE_FAILURE` | Deadlock retries exhausted; safe to retry with the same key |

## The database

Six tables in total; the schema grows one table per sprint (see
`backend/src/main/resources/db/migration`). Today:

| Table | Purpose |
| --- | --- |
| `accounts` | One row per account. `id` for joins and locking, `public_id` for the API. |

Rules the database enforces, not the application:

- A customer or merchant can never hold a negative balance. Only `SYSTEM_FUNDING` may, because it
  is the mirror image of the money inside the system.
- `public_id` is unique.
- Account type, currency and status are constrained to their allowed values.

`SYSTEM_FUNDING` is the counterparty for every deposit and withdrawal. It is the ledger's door to
the outside world: money entering steps in through it, money leaving steps back out.

## The plan

One vertical slice per sprint: one table, its entity and repository, its endpoint, and its tests
against real PostgreSQL. Nine sprints, then a release gate that proves the invariants.

The interesting work is not CRUD — it is correctness under failure:

| Sprint | Slice |
| --- | --- |
| 0 | `accounts` ✅ |
| 1 | `ledger_entries` (+ minimal `transactions`), append-only enforced by the database |
| 2 | `transactions` completed, posting service |
| 3 | Deposits and withdrawals |
| 4 | Transfers, rollback, deadlock-safe locking |
| 5 | `idempotency_keys`, retries and crash recovery |
| 6 | Concurrency hardening |
| 7 | Reconciliation job and admin endpoints |
| 8 | Release gate: invariants, 10,000-transfer gate, acceptance checklist |

See `Ledgerline Design, Requirements and Database Schema.md` for the full design, and
`docs/decisions.md` for the decisions taken along the way.
