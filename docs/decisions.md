# Decision log

One entry per decision worth explaining in an interview. Newest last.

## Sprint 0

### The API identifier is a server-generated UUID

`accounts.public_id` is a UUID generated by the server. Clients never supply it, and it is never
rewritten.

**Why:** the client cannot be trusted to pick a unique, unguessable, non-sequential value, and a
sequence-based id leaks business volume. Generating it server-side means the create call is a plain
`POST` and the response hands back the handle for every later call.

**Rejected:** client-chosen id (races, collisions, and it makes "does this already exist?" a
client problem); email as the key (mutable, PII, not a safe natural key for a ledger); a separate
`external_id` column (this project has no upstream system to correlate with, so it would be a
column with no writer).

### The API is versioned under `/api/v1`

**Why:** the contract changes as sprints land (`/accounts` becomes `/api/v1/accounts` once money
movement needs its own error shapes). A version prefix from day one costs one path segment and
removes the need for a later breaking-change migration.

**Trade-off:** the design document originally listed unversioned paths. The document was updated to
match; see the API contract table.

### Accounts are created, but only because this project has no upstream

In a real payments system, account opening belongs to core banking or KYC, and the ledger is told
about accounts. This project has no upstream, so `POST /accounts` is the seam where that data would
enter. It is a stand-in for an integration, not a product feature.

### The transaction engine never mutates account attributes

Only `balance_paise` is written by the money path. `owner_name`, `type` and `currency` are written
once at creation; `status` exists so an account can be frozen, and is only ever set outside the
transaction path. There is no generic account update endpoint: in an append-only ledger, the only
way to stop an account moving money is a status flag, not a delete.

### Errors are returned as a code plus a message

`{code, message, timestamp}` with a fixed HTTP status per code, handled by a single
`@RestControllerAdvice`.

**Why:** clients branch on a stable code, not on prose. It also stops Spring's default error page
from leaking a stack trace — the first version of this API did exactly that.

### One Testcontainers container per test run, started manually

`AbstractContainerTest` starts PostgreSQL in a static block instead of using `@Container`.

**Why:** with `@Container` on a shared static field, the Testcontainers extension stops the
container when the first test class finishes, while Spring's test context cache still points at
that database — the next class fails with `Connection refused`. Starting it once keeps the context
cache valid and cuts the suite from ~60s to ~10s.

### Testcontainers 1.21.4, not 1.21.3

Docker Engine 29 refuses API versions below 1.40; the docker-java bundled in Testcontainers 1.21.3
asks for 1.32, so the engine answers `HTTP 400` and Testcontainers reports a misleading
"Could not find a valid Docker environment". 1.21.4 negotiates a version the engine accepts.

### Flyway migrations are immutable once committed

`V1__init.sql` was edited freely only while it was uncommitted and applied nowhere. From Sprint 1
on, every schema change is a new numbered migration. Editing a shipped migration breaks Flyway's
checksum check and, worse, leaves environments silently out of sync.

## Retrospectives

### Sprint 0

- **Keep:** writing the test for the database rule, not just for the API. The negative-balance
  CHECK is the project's core promise, and proving it at the storage layer is what makes it
  credible.
- **Change:** the first error message we saw was a Jackson parse error about a "number 500". The
  actual cause was an HTTP 500 three layers down. When a test fails with a puzzling message, check
  the status code before the payload.
